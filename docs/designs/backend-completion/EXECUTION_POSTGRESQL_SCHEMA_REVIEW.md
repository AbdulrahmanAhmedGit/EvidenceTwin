# EvidenceTwin V1 — Concrete execution schema and SQL review

**Status: Recommended for owner approval.** Review date: 2026-11-06. All **24 gates remain OPEN**. These are documentation-only schema and SQL specifications, not migration files or executable implementation. No SQL below has been executed. Scope is the first isolated execution-infrastructure increment, not the complete hosted/scientific backend.

## 1. Decisions and evidence boundary

Retain PostgreSQL, SQLAlchemy Core exclusively, Psycopg 3, Alembic, Read Committed, conditional/version guards and the approved Job/Attempt state machines. Recommend PostgreSQL 18.6 and Python 3.14.4 as the initial development/test baseline, subject to current patch/security recheck when implementation is authorized. No cloud provider, region or managed service is selected.

The schema below is the complete proposed physical execution schema for this increment. Metadata belongs in one Core tables.py. It creates no researcher accounts, scientific calculations, claim verdicts or object-storage service. Opaque references point to future authoritative application services. Unconfigured production authorization, evidence-readiness, validation and execution-stop adapters reject affected work; test fixtures alone supply controlled implementations.

Use schema `et_execution`, created only by an explicitly invoked reviewed migration. SQL below omits the repeated schema prefix for readability; migrations and repositories must qualify all tables. No arbitrary search_path or caller-controlled identifiers. UUIDs are generated by the application without a database extension. All constraints/indexes use deterministic names in Core/Alembic. Explicit names in this specification are normative proposals; unnamed row-local CHECKs receive metadata convention names derived from table/column/purpose, never anonymous production names.

  id uuid PRIMARY KEY,
  owner_ref text NOT NULL REFERENCES dispatch_accounts(owner_ref),
  snapshot_id uuid NOT NULL,
  state text NOT NULL CHECK (state IN ('queued','running','retry_wait','reconciliation_required',
    'cancellation_requested','succeeded','failed','cancelled')),
  version bigint NOT NULL CHECK (version > 0),
  fence_counter bigint NOT NULL DEFAULT 0 CHECK (fence_counter >= 0),
  attempt_count integer NOT NULL CHECK (attempt_count > 0),
  max_attempts integer NOT NULL CHECK (max_attempts > 0 AND attempt_count <= max_attempts),

  id uuid PRIMARY KEY,
  job_id uuid NOT NULL REFERENCES jobs(id),

  CONSTRAINT uq_attempt_ordinal UNIQUE(job_id,ordinal),
  CONSTRAINT ck_attempt_lease CHECK ((state='running')=(lease_until IS NOT NULL)),
  CONSTRAINT ck_attempt_running_owner CHECK (state<>'running' OR (owner_instance IS NOT NULL AND fence IS NOT NULL)),
  CONSTRAINT ck_attempt_owner_pair CHECK ((owner_instance IS NULL)=(fence IS NULL)),
  CONSTRAINT ck_attempt_pending_owner CHECK (state<>'pending' OR (owner_instance IS NULL AND fence IS NULL)),
  CONSTRAINT ck_attempt_end CHECK ((state IN ('succeeded','failed','abandoned','cancelled'))=(ended_at IS NOT NULL))

CREATE UNIQUE INDEX uq_attempt_executable ON attempts(job_id)
  WHERE state IN ('pending','running','cancellation_requested');
ALTER TABLE jobs ADD CONSTRAINT fk_job_current_attempt
  FOREIGN KEY(id,current_attempt_id) REFERENCES attempts(job_id,id) DEFERRABLE INITIALLY DEFERRED;

  command_sha256 bytea NOT NULL CHECK (octet_length(command_sha256)=32),

  safe_reason text,
  response_refs jsonb NOT NULL,

  payload_schema text NOT NULL,

  payload_sha256 bytea NOT NULL CHECK (octet_length(payload_sha256)=32),

  CONSTRAINT uq_publication_revision UNIQUE(job_id,attempt_id,kind,logical_key,revision),
  CONSTRAINT uq_publication_job_id UNIQUE(job_id,id),
  CONSTRAINT uq_publication_attempt_id UNIQUE(job_id,attempt_id,id),
  CONSTRAINT fk_publication_predecessor FOREIGN KEY(job_id,predecessor_id) REFERENCES publications(job_id,id),

CREATE UNIQUE INDEX uq_publication_final ON publications(job_id) WHERE kind='final';
ALTER TABLE jobs ADD CONSTRAINT fk_job_final_publication
  FOREIGN KEY(id,final_publication_id) REFERENCES publications(job_id,id) DEFERRABLE INITIALLY DEFERRED;

  id uuid PRIMARY KEY,
  job_id uuid NOT NULL,
  attempt_id uuid NOT NULL,

  CONSTRAINT fk_step_reused FOREIGN KEY(job_id,reused_from) REFERENCES steps(job_id,id),

  byte_count bigint NOT NULL CHECK (byte_count >= 0),

CREATE INDEX ix_audit_job_time ON audit_events(job_id,occurred_at,id);

Recommend fixed internal owner/resource references limited to 512 Unicode characters by contract validation; client keys capped above; reject oversized manifests/output instead of silently truncating. Metadata bytes contain references/structured outputs, never file contents. Resource-limit values here are development-only recommendations; they do not approve scientific ingestion/pilot limits. Table control has exactly the two reviewed seed rows, initialized by the explicit migration; its sequence increments reject BIGINT exhaustion. Capacity scope initialization is an explicit administrative step, not automatic schema startup.

## 3. Cross-row enforcement and immutable records

The DDL deliberately does not pretend that CHECK can validate other tables. Under the queue/guard lock protocol, validate the full paired candidate before committing:

- Job current attempt is the unique executable attempt where required; attempts.ordinal equals the reserved ordinal and never exceeds jobs.max_attempts. Queue enabled/pending relation matches queued/retry_wait; every other state has queue disabled. A terminal job has no executable attempt.
- Job owner/case and snapshot guard kinds, ownership, pinned versions/digests and eligibility match. The snapshot manifest includes evidence/data/source versions, researcher-confirmed classification/bindings, policy/procedure/schema and execution/model/prompt configurations; missing mandatory confirmation blocks affected commands.
- A final publication belongs to the job's successful current attempt, has kind final and passes validation; a step publication matches its attempt/step. Predecessors and reused_from stay within the same authorized job/snapshot. Cycles and foreign-attempt relabeling reject. No cross-job step reuse in this increment.
- A reservation's external operation, if any, belongs to its exact job/attempt. Its scope type matches its use. Counter equals live reservations under a locked scope row. Releases are idempotent conditional updates with stored evidence, never inferred from job terminality.
- Hashes are recomputed from exact bytes; equality of hash alone is insufficient for identity or authorization. Immutable snapshot/publication/step/artifact content and completed attempt history are never updated by ordinary repositories. Corrections create new records; approved deletion follows a separate lifecycle.

Grant migration ownership only to the migration role. Runtime roles have no DDL/TRUNCATE privilege; mutations go through reviewed repositories. Separate worker/reconciliation roles should have only their necessary table actions; guard-changing authorization is not inferred from SQL access. A compromised or privileged direct SQL writer is outside repository correctness and must be addressed by deployment least privilege/audit gates. Do not implement a broad DELETE cascade: retention/deletion and accepted-reference cleanup require a later authorized transaction plan. Internal tests may clean only their disposable database/schema.

No trigger-written state machine is recommended: explicit conditional repository writes plus row-local constraints, composite FKs and partial unique indexes are easier to inspect. Trade-off: all writers must participate; a raw SQL path that bypasses the paired validator is a defect, even when its individual statements satisfy DDL constraints.

## 4. Final lock order and queue/admission algorithm

Use the earlier queue-first lifecycle protocol. Refine it with these explicit entry paths; no new global lock on every heartbeat/publication:

- Submission: lock control admission, then authority/snapshot guards, then insert new job/attempt/queue/account-dispatch records. Count all admitted nonterminal jobs under admission serialization. Recommend conservative development admission bounds of 16 outstanding globally and four per account, including running/retry/reconciliation jobs. This is stricter than pending-only bounds and prevents retries bypassing admission. Only new submission increases outstanding jobs; retry stays inside its existing admitted slot. Terminal transitions may decrease counts concurrently; conservative overcount/rejection is safe. Admission bounds remain unapproved for pilot.
- Claim: lock control dispatch; choose the least-recently dispatched account with an eligible head-of-line job; lock its queue candidate FOR UPDATE SKIP LOCKED; acquire the applicable guard and capacity rows in sorted order; then job, attempt, operations/publications. Update dispatch sequence only after a successful claim. Recheck FIFO and readiness under the locks. Retry deadlines preserve FIFO within account; a delayed oldest pending job may block that account temporarily, not other accounts. Never skip an older eligible row within the same account to overtake it: if its row is locked, try another account or return no claim.
- All other job writes: queue row first, then authority guards, snapshot/policy/configuration/artifact guards, capacity scopes, job/attempt/external/step, operation/publication relations, always sorted by stable key within a category.
- Guard-only revocation: acquire required guards in category/key order without queue rows. Never acquire an earlier category afterward. Follow-up job cancellation is a new queue-first transaction. Candidate publication holds the same relevant guard locks, so revocation either precedes it and blocks it, or follows it in the protected order.
- Never acquire admission/dispatch controls from a transaction already holding queue/guard/entity locks. A guard-only process must never later request a queue row in that same transaction. No transaction batches several unrelated jobs; multi-job administrative actions use individually guarded operations.

This avoids queue-first versus job-first deadlock cycles in the earlier prose. Allocation index uniqueness handles simultaneous creation; index conflicts are not an excuse to retry an external call. If a numeric capacity reduction is below live usage, reject the configuration update until drained rather than pretending permits disappeared.

## 5. SQL templates — documentation only

Values shown as `:names` are bound parameters supplied through Core, never formatted strings. Preceding ordered lock acquisition is part of each template's contract; snippets are not standalone replacements for PG01–PG12.

```sql
-- Queue candidate within selected account; scheduler row is already locked.
SELECT job_id, pending_attempt_id, version
FROM et_execution.queue_entries
WHERE owner_ref=:owner AND enabled AND ready_at<=clock_timestamp()
ORDER BY submission_order LIMIT 1 FOR UPDATE SKIP LOCKED;

-- Capacity reservation: caller holds queue/guard/scope locks; all required scopes
-- reserve in one transaction or all changes roll back. Insert reservation too.
UPDATE et_execution.capacity_scopes
SET in_use=in_use+1, version=version+1
WHERE key=:scope AND version=:expected_version AND in_use<capacity
RETURNING key,version;

-- New claim epoch: validate job/attempt/guards, replace expected predecessor only.
UPDATE et_execution.jobs
SET fence_counter=fence_counter+1, version=version+1,
    state='running', updated_at=:accepted_at
WHERE id=:job AND version=:expected_job_version
  AND current_attempt_id=:attempt AND state IN ('queued','retry_wait')
  AND fence_counter<9223372036854775807
RETURNING fence_counter,version;

-- Heartbeat after ordered locks and fresh command/idempotency checks.
WITH t AS MATERIALIZED (SELECT clock_timestamp() AS accepted_at)
UPDATE et_execution.attempts AS a
SET lease_until=t.accepted_at+make_interval(secs=>:lease_seconds),
    version=a.version+1
FROM t,et_execution.jobs AS j
WHERE a.id=:attempt AND a.job_id=j.id AND j.id=:job
  AND j.current_attempt_id=a.id AND j.state='running'
  AND a.state='running' AND a.owner_instance=:owner_instance
  AND a.fence=:fence AND j.fence_counter=:fence
  AND a.version=:expected_attempt_version AND a.lease_until>t.accepted_at
RETURNING a.lease_until,a.version;

-- Conditional final transition: staged/validated result acceptance is in this
-- same transaction, after ALL required fact locks and validation binding checks.
WITH t AS MATERIALIZED (SELECT clock_timestamp() AS accepted_at)
UPDATE et_execution.jobs AS j
SET state='succeeded',final_publication_id=:publication_id,
    version=j.version+1,updated_at=t.accepted_at
FROM et_execution.attempts AS a,t
WHERE j.id=:job AND j.version=:expected_job_version AND j.state='running'
  AND j.current_attempt_id=:attempt AND j.snapshot_id=:snapshot
  AND j.fence_counter=:fence AND a.id=:attempt AND a.job_id=j.id
  AND a.state='running' AND a.owner_instance=:owner_instance
  AND a.fence=:fence AND a.version=:expected_attempt_version
  AND a.lease_until>t.accepted_at
RETURNING j.id,j.version,t.accepted_at;
```

Immediately before time sampling, acquire all locks that could wait, including the operation-key conflict/uniqueness protection. The materialized time CTE is issued only after those earlier lock statements complete; it is not relied on to sample after waits inside its own statement. No network work or deliberate sleep occurs afterward. The protected operation's linearization point is the accepted conditional transition, not client receipt or later wall-clock commit acknowledgement. Accepted transitions still require commit; failure rolls everything back.

Final publication transaction order: lock/context checks; resolve scoped operation collision; validate canonical payload binding and staged artifacts; insert accepted operation/publication with deferred final pointer relation; run the conditional final transition; update attempt to succeeded clearing lease/setting ended_at; disable queue; insert accepted step/artifact links and audit; conditionally release only settled reservations; commit. Exactly one expected row per single-target update is mandatory. Any mismatch raises rollback and separately records safe rejection if possible. The deferred FK permits job/publication/attempt creation ordering, but does not waive final paired invariants.

Claim transaction also updates attempt pending→running with returned epoch, owner and `accepted_at+lease`, disables queue without deleting its coordination row, inserts analysis reservation and audit, and commits. A claim is never acknowledged before commit. No call occurs inside a transaction or its retry closure.

## 6. Idempotency and rejection protocol

Unique scope is owner_ref/resource_ref/kind/client_key. Recommend canonical command schema `execution-command-v1`: UTF-8 JSON with keys sorted, no whitespace, ensure_ascii false, no duplicate keys, integers/booleans/null/strings/arrays/objects only. Decimal/duration inputs use explicit decimal strings; binary floats and non-finite tokens reject. Preserve original scientific tokens as strings or immutable artifact references. Compare exact canonical bytes and schema plus digest; a digest is not sufficient. Client keys are opaque bounded strings, not credentials.

Fresh command inserts its operation only in the transaction that commits acceptance/rejection. An existing equal operation returns the same authorized committed response references without mutation. A conflicting command key produces a separate conflict audit event referencing only authorized existing metadata, never rewrites the original operation. On insertion conflict under Read Committed, read the committed winner in a subsequent statement and compare; do not use a same-statement visibility assumption. Authorize response reads again even for a prior accepted key.

Expected guard rejection can commit a rejected operation plus safe audit without active mutation. If speculative writes occurred, roll back that transaction first and run a fresh authorized rejection-record transaction using the same immutable command identity. It must check whether another accepted outcome already exists and cannot overwrite it. If connectivity/commit is unknown, return an indeterminate operation state and reconcile; do not fabricate durable audit success. A completely unavailable database cannot guarantee rejection-audit persistence.

## 7. Database-only retries — final recommendation

Recommend three total database-operation executions, with full jitter upper bounds 50 ms then 100 ms (200 ms configurable maximum), for explicit PostgreSQL deadlock 40P01 and serialization failure 40001 only. Retry the entire short transaction, fresh guards, same operation identity and immutable prepared payload. Ordinary Read Committed does not rely on Serializable; 40001 handling exists for reviewed selective use or server behavior. Never retry validation, permission, unique key conflict, exhausted capacity, unsupported configuration or schema failure as a generic transient exception.

Heartbeat operations instead get one transaction execution per scheduled heartbeat, within the existing two-second end-to-end deadline; a lost acknowledgement is reconciled rather than extending the lease again. A future scheduled heartbeat is not a replay of an uncertain operation. Recommend pool checkout one second, lock_timeout 500 ms, statement_timeout one second, idle_in_transaction_session_timeout two seconds, connect_timeout two seconds, pool_size two and max_overflow zero per execution process. All are development-only additions, not pilot settings. Repository command wall-clock deadline is two seconds including pool/lock/commit acknowledgement; do not reset it across database retries. Deadline cancellation can leave commit unknown and therefore requires operation reconciliation. No automatic retry on class 08 connection failure/unknown COMMIT outcome. 55P03 lock timeout returns contention without allocating a scientific retry; dispatcher tries again on a later poll.

The approved scientific execution retries remain three total attempts, base two seconds, max fifteen seconds and full jitter as already specified; do not substitute these database retry values. Recommend a configurable two-second poll as the selected default inside the approved 1–3-second range. No paid call, object upload, task launch or irreversible side effect belongs inside a retried transaction.

## 8. Worker-stop, artifacts and security review

Recommend supervisor-owned per-attempt subprocesses for the first same-host execution worker. Parent creates no shared live Engine across process boundaries; every process creates/disposes its own Core Engine. Stop-new-work on uncertain lease, then cooperative stop, then supervisor termination and confirmed process-group reaping before analysis capacity release. Retain the reservation if the original instance cannot be proven stopped, such as across host loss; operator recovery can record attributable host/process-stop evidence. Process IDs alone, hostnames or lease expiry are not proof. External calls remain separately unresolved even after confirmed local process exit.

A worker must reconcile a committed dispatch intent and ownership immediately before sending. There is still an unavoidable boundary between the database and the network; a crash/cancellation there may leave a request uncertain. Serialize launch through the supervisor's local execution gate and deny launches after observed cancellation. Do not promise instantaneous remote cancellation or exactly-once provider execution. Persist uncertainty and hold permits instead. This limitation does not authorize blind replay.

Provide explicit interfaces for current principal/action authorization; guard synchronization; immutable snapshot/configuration lookup; validation binding; artifact readiness/acceptance/deletion; trusted execution-stop proof; and external settlement evidence. Production implementations absent in this increment return unavailable. No test authorizer/validator is exported or auto-selected by production configuration. No external IdP, storage provider, scientific capability or paid-provider adapter is implemented in this first increment.

Use owner-scoped lookups on reads as well as writes, safe non-enumerating failures, TLS verification for nonlocal database connections, DSNs/secrets outside logs, no stored provider keys in these tables and no unauthenticated execution HTTP endpoint. Migration/operator credentials never reach workers. Artifact object_ref is not a public URL; exact-version/hash readiness is verified by the adapter, and accepted download/export paths remain unavailable until the real private-storage/authorization bridge is approved.

## 9. SQL/schema review conclusions

Manual design review identified and resolved: queue/job reverse lock ordering; missing-row admission races; attempt cap bypass through retry; current-attempt cross-job references; successful result pointer cycles; nullable uniqueness; premature capacity release; clock sampling before lock waits; operation-key conflict visibility; and treating database retries as scientific attempts. DDL constraints and transaction proof are complementary. No SQL parser/server/migration test was run, so syntax, plans, driver behavior and race guarantees remain implementation acceptance obligations, not proven facts.

Schema, algorithms and numeric additions above are assistant recommendations, not owner-approved gate closures.

## 10. Final review refinements and readiness baseline

Composite FKs now additionally constrain publication predecessors to the same job, steps to the exact producing attempt/publication, reused steps to the same job and external reservations to the exact call's job/attempt. Add FK-supporting indexes on steps(publication_id), publications(attempt_id), reservations(external_operation_id) and audit_events(operation_id) in Core metadata/migration; these are recommended small, predictable lookup indexes, not measured query-plan optimization. Artifact owner/object/version is unique to prevent conflicting registered identities.

Constraint naming: primary keys use pk_<table>; inline FK names use fk_<table>_<column>_<referenced table>; unnamed row CHECKs in this review receive ck_<table>_<two-digit declaration ordinal>. Named constraints shown above retain their names. This is a deterministic mechanical mapping for the future migration, not an unresolved product decision. Check names before final migration compilation for duplicate/truncated collisions (PostgreSQL identifier length limits apply).

Recommend same-host process cleanup development defaults: cooperative stop grace two seconds, termination wait two seconds, then kill and a two-second confirmed-reap wait; if exit cannot be confirmed, hold capacity and surface reconciliation. For cancellation, logical terminalization may complete without declaring process/provider settlement. These are development-only settings, not validated hosted failover behavior. Keep a worker-instance identity and process-group/start identity in safe execution audit; never trust a reused OS PID as proof. No host/process is killed during this design work.

The complete specification is ready for coding-scope review. SQL snippets are reviewed templates, not a claim that the first migration is already syntactically/server validated. Implementing, compiling and exercising the specification against PostgreSQL is the authorized coding stage's job; it does not require selecting another architecture halfway through development. Any new architectural incompatibility discovered during implementation must be reported before silently changing this scope.

## 11. Required internal command and adapter contracts

Snapshot manifest schema `execution-snapshot-v1` requires: internal owner/case/analysis revision; immutable evidence snapshot ID and manifest ID/hash; exact source/dataset/selection revision references; confirmed classification/binding revision references or explicit preliminary blockers; scientific policy/procedure/schema references; execution configuration/model/prompt/protocol references; expected evidence/policy/configuration guard versions and content hashes; declared review mode and output contract. A manifest does not certify that scientific checks occurred. The normalized manifest stores references and original token representations, not private file bodies.

Every mutating command requires trusted principal/action context, operation ID/key, schema version, job/resource reference, expected record versions and exact command content. Worker commands additionally require attempt, owner instance, epoch, expected lease revision and snapshot identity. Control commands use explicit authorized action/predecessor, not fabricated worker ownership. Snapshot registration and guard eligibility updates are trusted application-service operations unavailable without configured authority; test seeding is not an HTTP service.

Required adapters and safe defaults:

| Adapter | Input → trusted output | Default without implementation |
| --- | --- | --- |
| Authorizer | Current internal principal, resource/action and locked authority/case context → authorized decision with attributable guard version | Deny/unavailable; no test user or operator privilege fallback. |
| Snapshot/configuration resolver | Exact immutable refs and expected hashes → version-admissible immutable manifest | Unavailable; no latest lookup or model fallback. |
| Candidate validator | Full result/check payload, pinned schema/policy, observation/provenance refs → exact content-bound validation record | Unavailable; no caller-supplied true/valid flag. |
| Artifact readiness | Owner, immutable object/version/hash and locked eligibility guard → current authorized readiness record | Unavailable for artifact-dependent publication; no existence-only verification. |
| Execution-stop proof | Original worker instance/process group/start identity → confirmed local process exit or explicit unknown | Unknown retains analysis reservation. |
| External settlement | Original logical request/provider reference plus attributable evidence → settled/not-sent/unknown with reservation effects | Unknown retains permits; no inferred remote cancellation. |

Observations, scientific determinations and provenance remain separate logical records in the versioned payload/manifest; the infrastructure does not merge them into execution success. Any future real scientific adapter must satisfy its own existing acceptance gates before enabling publication of that scientific result type.

Internal repository outcomes are distinct typed branches: Accepted, Rejected(code), Conflict, CapacityUnavailable, Contention, IntegrationUnavailable and CommitUnknown(correlation/operation reference). Do not expose these internal records directly as public `/api/v1/` DTOs. Error/log text contains safe codes and opaque correlation only; no DSNs, source passages, keys, arbitrary database diagnostics or existence leaks. Outage diagnostics cannot be called a durable database audit.

Physical-send versus cancellation remains a cross-system integration limit: a request already authorized as a committed dispatch intent may still be physically in flight when cancellation is accepted. Record the original attempt and treat late outcomes as settlement only. This first increment sends no real provider traffic. A later real-provider bridge must independently review its launch/cancellation/settlement contract under E06; the infrastructure does not promise remote exactly-once behavior or atomic database/network cancellation.

## 12. Lost-acknowledgement replay ordering clarification

Resolve an already committed operation after current resource/response authorization but BEFORE requiring current worker lease, fence or nonterminal state. An exact authorized replay may return its prior accepted outcome even when that job has since become terminal or ownership changed; it performs no new active mutation and does not assert that the old worker is current. New/conflicting commands still require all applicable current guards. This distinction prevents successful terminal publication followed by lost acknowledgement from being misreported as a failed new publication. Cancellation/permission changes can still deny access to the historical response.

For a fresh command, no prepared payload becomes accepted until all current mutable guards and the paired transition commit. Rejected stale commands do not overwrite the old operation. This order is part of the repository contract and EX06/EX20/EX27/EX39 must exercise it explicitly.

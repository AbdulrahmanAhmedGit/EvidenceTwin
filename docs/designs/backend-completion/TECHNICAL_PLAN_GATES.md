## Gate rules

- **Decision (D):** resolve the named design choice, specification or public contract and obtain explicit approval before implementing the affected part.
- **Enablement (E):** approve the scientific/capability specification, implement only under separate authority, and produce the required acceptance evidence before exposing that capability as operational.
- **Pilot (P):** resolve and validate hosted operating, privacy, access and recovery requirements before accepting the corresponding pilot work.
- Closing one gate does not close another. Adoption of a policy direction, route registration, successful HTTP responses, passing schema validation and model agreement cannot close scientific acceptance gates.
- An unimplemented or blocked capability remains explicitly unavailable. Supported sub-capabilities need their own declared scope; unsupported parts cannot silently inherit an enabled flag.
- A gate record needs an approved scope/version, decision rationale, named approval authority, relevant evidence/test references, approval time and any remaining restrictions. No placeholder result counts as evidence.
- Core/API/prompt/evidence versions remain independent. Changes must identify which specifications and prior acceptance evidence they affect; no automatic continued approval after a material change.
- Numeric values are proposed/tested/approved separately. The already-approved concurrency planning caps remain 2 analyses, 1 LLM request per analysis and 2 globally; that approval is not measured capacity.

## Closing evidence and sequencing

1. Finish the affected Decision artifact and obtain its explicit approval. Comparative research and specification drafting are still design work, not production implementation authority.
2. Obtain separate authority before writing production code or deploying. Implement the approved scope and produce the corresponding Enablement evidence; keep the flag unavailable until its acceptance requirements are satisfied and approved.
3. Validate the cross-cutting Pilot gates against the actual selected deployment and configuration before admitting users/work. Do not treat tests against mocks as tests of an unconfigured external service.
4. Reopen affected validation when its policy/version/configuration changes. A narrower genuinely accepted scope may be exposed only with honest coverage; do not waive mandatory checks to close a gate.
